## 原始数据的请求参数

这些是复现这批数据需要的全部信息：

| 参数 | 值 |
|---|---|
| `dataset` | `GLBX.MDP3` |
| `symbols` | **`NQ.v.0`** |
| `stype_in` | `continuous` |
| `schema` | `ohlcv-1m` |
| `start` | `2010-06-06`（GLBX.MDP3 数据集起点） |
| `end` | 见下（分两次拉） |

实际覆盖：`2010-06-07 00:00 UTC` → `2026-09-08 05:26 UTC`，约 **16.3 年**，共 4,814,864 根。

分两批：

| 批次 | 文件 | 范围 | 花费 |
|---|---|---|---|
| 初次 | `NQ_v_0_1m_2010_2017/2018_2022/2023_2026.parquet` | → 2026-08-28 20:59 | $18.83 |
| 增量 | `NQ_v_0_1m_2026_fwd.parquet` | 2026-08-26 → 2026-09-08 05:26 | $0.0457 |

增量那次**故意重叠了 08-26～08-28 三天**（4,020 根）。
`scripts/fetch_databento.py` 会把重叠段和已有的 `nq_1m.parquet` 逐棒比对，
OHLCV 全部相同才写档 —— 参数如果重现不出原始序列（时间戳约定改了、
换了连续合约、bar 被修订），后面拿新资料算的所有东西都不可信，
而且事后才发现比多付两天的钱贵得多。**那次比对是 0 差异通过的。**

`ict/data.py::load_raw` 现在会把**内容完全相同**的重叠时间戳静默去重，
内容不同的直接报错 —— 不让 `drop_duplicates` 随机挑一份。

### 拉取时间的上限

Databento 对 CME 最近的资料要另外的订阅。这个 key 在 2026-09-08 当天
只能拉到 `2026-09-08T05:27:23Z` 为止（再新的会回 `dataset_unavailable_range`）。
所以完整的 RTH session 到 **2026-09-07** 为止。

### ⚠ 为什么是 `.v.0` 而不是 `.c.0`

**这一条如果选错，整个回测就是虚构的。**

- `.c.0` = **日历排序**连续合约 —— 到期周仍然停在**将死的近月**上
- `.v.0` = **成交量排序**连续合约 —— 跟着实际主力走

我一开始用的 `.c.0`，在试点里发现了：**2024-09-20 那天 09:30 那一小时，
`.c.0` 只有 380 手，`.v.0` 有 68,278 手。** 在 380 手的合约上回测出来的成交价没有意义。

换成 `.v.0` 重拉，那次错误浪费了 $1.28。

## 字段

**1 分钟文件：**

| 列 | 类型 | 说明 |
|---|---|---|
| `ts` | `datetime64[ns, UTC]` | bar **开始**时间，UTC |
| `open` / `high` / `low` / `close` | `float64` | 价格，0.25 跳 |
| `volume` | `uint64` | 手数 |

**5 分钟文件**：同上，另加 —

| 列 | 说明 |
|---|---|
| `ema12` | EMA12，α = 2/13，用**前 12 根的 SMA 播种**（不是从第一根开始递推） |
| `atr14` | Wilder ATR14，α = 1/14，同样 SMA 播种 |

前 11 根的 `ema12` 是 `NaN`，前 13 根的 `atr14` 是 `NaN`——这是正确行为，不是缺数据。

### 5 分钟是怎么聚合的

按 **UTC 整点边界**（`origin="epoch"`）聚合，不是按 ET。

这样是安全的，因为纽约开盘 09:30 ET 在夏令时落在 13:30Z、冬令时落在 14:30Z，
两个都正好是 5 分钟边界。信号 bar 的选取是用 `zoneinfo` 按 `America/New_York`
的本地时间判断的，所以夏令时切换会被正确处理。

**指标跑在 24 小时连续时段上**，不是只有 RTH。这一点很重要：
RTH-only 的图表会算出**不同的 EMA**，从而给出不同的信号，而且不会报错。

**这是我从抓取日志里抄下来的，共 11 天，但这个清单可能不全**——
Databento 的警告信息本身是截断的（结尾是 `...`）。

`2026-08-29` 是增量那次抓取时 Databento 警告的（那天是周六，不影响 RTH）。

我本想用 `metadata.get_dataset_condition`（免费）复查一次完整清单，
但环境里没有常驻的 API key。你想要准确清单的话自己跑一下：

```python
import databento as db
c = db.Historical("<你的 key>")
cond = c.metadata.get_dataset_condition(
    dataset="GLBX.MDP3", start_date="2010-06-06", end_date="2026-08-29")
print([r["date"] for r in cond if r["condition"] != "available"])
```

**我没有剔除这些天**——它们照常进入了回测。16.2 年里的十来天，
影响可以忽略，但你应该知道它们存在，而不是以为数据是完美的。

## 复现 / 增量拉取

```bash
DATABENTO_API_KEY=<你的 key> uv run python scripts/fetch_databento.py \
    --start 2026-09-05 --end 2026-09-12 --max-cost-usd 1.00

uv run python scripts/ingest.py        # 合并 + 延长 5m + 校验
```

`fetch_databento.py`：

- **key 只从环境变量读**，不接受命令列参数 ——
  参数会进 shell history，也会出现在 process list 里，同机器上任何程序都看得到。
- 下载**之前**先呼叫 `metadata.get_cost`，超过 `--max-cost-usd`（预设 1.00）就中止。
  `--dry-run` 只报价不下载。
- 预设会重叠比对（见上）。`--no-verify-overlap` 可以关掉，但没有好理由关。

`ingest.py` 会把 5 分钟档一起延长：只 append 出厂范围之后的 bar，
`ema12` / `atr14` 在合并后的完整序列上重算，
**写档前先确认重算值在出厂范围内与出厂值差 0.0**，
所以延长不可能悄悄改写十六年的指标历史。
另外会断言 1m 与 5m 的结尾不能差超过两根 5 分钟 ——
否则七套 session 策略会静默地少跑几天。

### ⚠ key 的处理

**API key 出现在对话里就等于外泄了，用完立刻去 databento.com 撤销并换新的。**
这件事发生过两次（第一次拉全量、第二次拉增量）。
正确做法是设成环境变量，不要贴进对话。
